# AI Integration: where to customize

All model-related code lives in **`backend/app/ai/`**. The rest of the app never imports OpenAI, LangChain or Chroma directly; it calls the small interfaces in this folder. The same map is shown live in the app under **AI integration** (sidebar), which reports which components are configured. It never shows secret values.

> **Secrets:** nothing is hardcoded. Set keys as environment variables or in your platform's secret store (Docker secrets, Vercel/Railway/Render env, Kubernetes Secrets, ...). For local work copy `.env.example` to `.env` (git-ignored).

## Behaviour without AI configured

| Capability | With `OPENAI_API_KEY` | Without |
|---|---|---|
| Project demand → required skills | LLM extraction (`ai/tasks.py`) | Keyword matching against the taxonomy; you edit the result anyway |
| Skill standardization | exact → fuzzy → semantic (embeddings) → configured Jev or LLM pick | exact → fuzzy → placeholder-embedding match → flagged for review. `app/data/skill_taxonomy.json` is authoritative for bundled skill categories; startup reconciles SQLite taxonomy and employee-skill rows, and refreshes changed vector metadata. User-created taxonomy entries retain their own categories. |
| Staffing | complementary team (each member adds skills the team lacks); deterministic skill/role checks plus Chroma entity retrieval and a local FlashRank cross-encoder rank candidates; study plans for skills nobody has | same, with **placeholder hashing embeddings** (lexical only) |
| Learning path | LLM-written Markdown from the gap + Jev-verified courses and videos | Template Markdown plan using Jev-verified courses |
| Free-text PDF extraction | LLM | Only tables and `Name: …` style PDFs |

Responses say which mode produced them (`mode`: `llm` / `heuristic` / `template`), and the UI shows it.
Jev decisions are enabled by `TYPESAFE_API_KEY`, independently of `OPENAI_API_KEY`. Without the Jev key, course results are omitted because they cannot be relevance-verified; gap risk uses the LLM and then the formula, and standardization uses its configured LLM or semantic/review fallback.

## Component map

| Component | File | Environment variables | What you customize |
|---|---|---|---|
| **LLM** (GPT-4.x / mini class) | `ai/llm.py` | `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `LLM_MODEL` | Model, provider (Azure, vLLM/Ollama serving a fine-tune), temperature, JSON mode |
| **Prompts** | `ai/prompts.py` | `PROMPT_STYLE_STANDARDIZE`, `PROMPT_STYLE_REQUIREMENTS`, `PROMPT_STYLE_GAP_RISK` | Every system/user prompt: standardization, PDF extraction, requirements, gap risk, study plan. Each of the three settings (`few` default, or `zero`) adds worked examples (few-shot) to standardization, requirements or gap risk; the other prompts are always zero-shot; the examples are lists at the bottom of `prompts.py` and contain no real data. Set a setting to `zero` for instructions only. Compare the two on your reviewed mappings to see which matches your decisions better |
| **LLM tasks** | `ai/tasks.py` | none | Parsing/validation of LLM outputs for each task |
| **Embeddings** (`text-embedding-3-small`) | `ai/embeddings.py` | `OPENAI_API_KEY`, `EMBEDDING_MODEL` | Swap the embedder. Vectors are stored per embedder name, so switching never mixes dimensions; then run **Re-index** |
| **Vector DB** (Chroma) | `ai/vectorstore.py` | `CHROMA_HOST`, `CHROMA_PORT`, `CHROMA_PATH` | Employee parents have searchable skill, role, domain, and background child entities with `employee_id`/`parent_id` metadata. Taxonomy skills are individual entities. Chroma `where` filters can constrain entity type, skill, rating, role, domain tag, or category. On startup, bundled taxonomy categories are reconciled into SQLite and existing employee-skill rows; changed taxonomy metadata and employee vectors are refreshed. Legacy employee vectors are also detected and rebuilt; use **Re-index** after embedding or storage changes |
| **Reranker** (FlashRank) | `ai/reranker.py` | local model `ms-marco-MiniLM-L-12-v2` | Cross-encoder reranks retrieved employee profiles and taxonomy candidates without sending employee text to a hosted reranking API. The model is loaded on first use; if unavailable, the app logs the issue and retains vector ordering |
| **Orchestration** (LangChain / LangGraph) | `ai/orchestration.py` | `ORCHESTRATION=sequential\|langgraph` | Add graph nodes (retrieval, critique, human approval) to `LEARNING_PATH_NODES` |
| **Caching** (Redis + GPTCache) | `ai/cache.py` | `REDIS_URL`, `CACHE_TTL_SECONDS`, `GPTCACHE_ENABLED`, `GPTCACHE_SIMILARITY`, `GPTCACHE_NAMESPACES` | Two layers: Redis = exact-match cache for LLM/embedding calls (in-memory fallback without `REDIS_URL`); GPTCache = opt-in *semantic* cache for the listed namespaces only. Tune TTLs, keys, namespaces |
| **Guardrails** (Guardrails AI / NeMo / Jev) | `ai/guardrails.py` | `GUARDRAILS_PROVIDER=none\|builtin\|guardrails_ai\|nemo`, `TYPESAFE_API_KEY` | Implement `_guardrails_ai_check` / `_nemo_check` (stubs raise `NotImplementedError`). Built-in checks include length limits, injection patterns, invented-link removal, and a **toxic / cursing language filter** (`ai/toxicity.py`, `data/blocked_terms.txt`; `GUARDRAILS_TOXICITY=off\|wordlist\|moderation\|both`): input that contains cursing or is flagged by the moderation model (harassment, hate) is rejected; the AI's answers get listed words masked or are withheld if only the model flags them. The moderation call needs `OPENAI_API_KEY`; `GUARDRAILS_MODERATION_FAIL=open\|closed` controls its failure behavior. With `TYPESAFE_API_KEY`, Jev also blocks requests to reveal sensitive personal data or secrets (contact details, government IDs, health information, passwords, API keys); ordinary skill-matrix/staffing questions are not classified as sensitive by that rule. A Jev outage follows `GUARDRAILS_PROVIDER_FAIL`; `GUARDRAILS_PROVIDER=none` disables the guardrail pipeline. Bulk uploaded employee text skips the Jev privacy check. |
| **Monitoring & tracing** (Langfuse / LangSmith) | `ai/tracing.py` | `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_HOST` or `LANGSMITH_API_KEY` | Decorator wiring per SDK version; add `@traced("name")` to any function |
| **Jev decision service** | `ai/jev.py` | `TYPESAFE_API_KEY` | Shared fixed-choice decisions used by standardization, gap-risk bands, course relevance, and sensitive-data guardrails. Standardization still uses `STANDARDIZE_MATCHER=jev` to select Jev; when Jev is unavailable it uses the LLM fallback. Gap risk maps Jev's Low/Medium/High decisions to `0.20`/`0.50`/`0.80` regardless of confidence, then falls back to the LLM and formula. Course picks are included only after Jev verifies relevance; unverified picks are omitted. |
| **Gap risk prediction** | `ai/predict.py` | `TYPESAFE_API_KEY`, `OPENAI_API_KEY`, `LLM_MODEL` | Jev makes a fixed Low/Medium/High decision, mapped to `0.20`/`0.50`/`0.80`; if Jev is unavailable or errors, the existing LLM score is tried, then the transparent formula. |
| **Evaluation** (RAGAS) | `ai/evaluation.py`, `ai/eval_log.py`, `ai/make_eval_dataset.py` | `OPENAI_API_KEY`, `EVAL_LOG_ENABLED`, `EVAL_RAGAS_API` | Staffing and learning-path answers are logged to `backend/data/eval/interactions.jsonl`. `python -m app.ai.make_eval_dataset` turns the log into `samples/eval_dataset.json`; `python -m app.ai.evaluation` scores faithfulness, answer_relevancy, context_recall, context_precision and answer_correctness. Ground truths are derived from your data: edit them. Staffing rows put the context that supports the reference first (RAGAS context_precision rewards that), log the whole suggested team, company-wide coverage counts and the computed scores as contexts, and a reference that names the best partial fits; learning rows log the request, the gaps and the time split as contexts. Log rows carry a format version; rows from older versions are skipped (the builder lists the questions to ask again; `--archive-old-log` moves them aside). **Ask the matrix** is evaluated too: `python -m app.ai.chat_eval --run` asks a fixed question set (generated from your data, each with an exact expected answer, plus two guardrail cases) through the real chat agent, and every question people ask on the chat page is logged with its answer and the data the tools returned. Real questions get the rule-based checks; RAGAS scores them once you write a `ground_truth` for them in the dataset file (`python -m app.ai.evaluation --kind chat`). Chat questions are stored in the evaluation log (turn off with `EVAL_LOG_ENABLED=false`). `python -m app.ai.eval_checks` runs exact rule-based checks (real people, true claims, hours add up, only retrieved links) with no key; `python -m app.ai.evaluation` runs them first and then RAGAS, retries unscored metrics once, and reports unscored rows and RAGAS errors instead of counting them as 0. `EVAL_RAGAS_API=legacy` (default) scores with `ragas.metrics` + `evaluate()`; `collections` uses `ragas.metrics.collections` of ragas 0.4+ (one `ascore` per row and metric, an instructor-style LLM from `llm_factory`); `auto` tries `collections` and falls back to `legacy`. The results file records which one ran. The `collections` path was checked against ragas 0.4.3's signatures and stubbed calls only, not a real run. Use `python -m app.ai.make_eval_dataset --replay --refresh-references` once after upgrading; afterwards a reference you edited by hand is recognised and kept. |
| **Golden-set evaluation** (recommended) | `ai/evaluation.py` (`--golden`), `samples/golden/people.json`, `samples/golden/golden_set.json` | `OPENAI_API_KEY`, `LLM_MODEL` | Fixed fictional people + hand-written ground truths. `python -m app.ai.evaluation --golden --runs 3` loads the people into a temporary database (your real data is never touched), runs every case through the app's own chat, staffing and learning-path code, and scores answer + contexts (from the app) against the golden ground truth with RAGAS; standardization is scored by exact match. Results are per feature with the spread across runs, provisional floors, the change since the previous golden run, and the judge model and RAGAS version, saved as `backend/data/eval/golden-<time>.json`. `--golden-check` (no key) verifies that the golden file agrees with the people file. Besides chat, staffing and learning cases it has exact-match standardization cases and guardrail cases (a question that must be refused). A metric with fewer than 80% of its rows scored is reported INCOMPLETE and RAGAS's errors are printed. Staffing answers now say why the best runners-up were not chosen (`not_chosen` in the staffing result, shown on the Projects page). Edit the two JSON files to grow the set |
| **Synthetic dataset evaluation** | `ai/evaluation.py` (`--fill-answers`) | `OPENAI_API_KEY`, `LLM_MODEL` | Score a hand-made JSON dataset (`question`, `contexts`, `ground_truth`, `answer: "PLACEHOLDER"`, `metadata.pillar`) without logs: `python -m app.ai.evaluation ../samples/ragas_synthetic_dataset.json --fill-answers --limit 3`. The LLM first fills each placeholder answer from that row's own contexts (saved as `<name>.answered.json`, your file is untouched); RAGAS then scores it, averaged per pillar. It tests the model and prompt, not the app's staffing or gap logic, and the rule-based checks are skipped. Without `--fill-answers`, a PLACEHOLDER answer is refused. `--from-app` instead takes the answers and contexts from the real app: each question goes through the Ask-the-matrix chat agent, the tool results are the contexts, and the ground truth stays from your file (saved as `<name>.from_app.json`, not added to the log) |
| **Agents** (standardization, intake, upload check, chat) | `agents/` (`runtime.py` loop, `tools.py`, `prompts.py`, `proposals.py`, one file per agent) | `OPENAI_API_KEY`, `AGENT_MAX_STEPS`, `AGENT_MAX_RUNS_PER_HOUR`, `TAVILY_API_KEY` | A bounded tool-calling loop on the configured chat model. Agents can only read or *propose*; `proposals.py` holds the role rules and what applying a proposal does. Edit prompts in `prompts.py`, add tools in `tools.py`. Only exact matches / earlier human decisions are auto-applied (`agents/standardization.py`). Not yet evaluated with RAGAS: tool-calling transcripts need their own test set. |
| **Fine-tuning** (Unsloth) | `ai/finetune/` | none | Export reviewed skill mappings → JSONL → train in a separate GPU env → serve behind an OpenAI-compatible endpoint → set `OPENAI_BASE_URL` + `LLM_MODEL` |
| **Learning content** (catalog + Microsoft Learn + YouTube) | `services/courses/` (`catalog.py`, `mslearn.py`, `youtube.py`, `__init__.py` mixes them) | `COURSE_SOURCES`, `COURSE_CATALOG_PATH`, `TYPESAFE_API_KEY`, `COURSE_CACHE_HOURS`, `MSLEARN_LOCALE`, `YOUTUBE_API_KEY`, `YOUTUBE_MAX_SEARCHES_PER_DAY`, `YOUTUBE_CACHE_DAYS` | Jev verifies relevance using course titles plus available descriptions and outcomes. Add optional `description` and `learning_outcomes` columns to `backend/app/data/course_catalog.csv`; Microsoft Learn summaries and YouTube descriptions are passed automatically. Jev only receives bounded-length text. Unverified results are omitted, including when Jev is not configured or its check fails. Microsoft Learn needs no key. `YOUTUBE_API_KEY` goes in `.env` or your platform's secret store (never in code); without it videos are skipped. Lookups are cached on disk and YouTube searches are capped per day. Add a source by writing `search(skill, level, limit)` and registering it in `services/courses/__init__.py` |
| **Udemy API** (optional extra source) | `services/udemy/` | `UDEMY_MODE`, `UDEMY_CLIENT_ID`, `UDEMY_CLIENT_SECRET` | Used only if `udemy` is in `COURSE_SOURCES`. Currently **sample data** (`mock`). `affiliate.py` is an untested starting client |

## Suggested order

1. Set `OPENAI_API_KEY` → check the **AI integration** page → re-upload or press **Re-index vectors**.
2. Tune `prompts.py` (especially `LEARNING_PLAN_*` and `REQUIREMENTS_*`).
3. Add Redis (`REDIS_URL`) and tracing keys.
4. Fill `course_catalog.csv`, set `YOUTUBE_API_KEY`, and replace the guardrail stubs.
5. Evaluate with RAGAS, then consider fine-tuning on reviewed mappings.

## Status of each piece (honest list)

- Verified by running against sample files, with stand-ins for Chroma / rapidfuzz / pydantic-settings: parsing (all four sample files), standardization flow, gap and staffing logic, template study plan, guardrails (injection block, invented-link removal), the LLM path with a *faked* model, and import of `main.py` + all 22 routes against a stubbed `fastapi`.
- Login, roles and the audit log (service logic) and the agents were verified with a **scripted fake chat model**: approval-queue role rules, auto-apply of exact matches, ask-the-user pause/resume, step limit, run privacy, audit of chat questions, upload check dry runs. A real model choosing tools well (and the real `bind_tools` call shape), Tavily, and the new pages are **not** verified.
- **Not run:** the HTTP layer itself under real FastAPI/uvicorn, and the Next.js frontend (`npm install` / `next build`); the package registries were unreachable when this was last worked on.
- The course sources were tested with **stubbed HTTP responses** (catalog parsing and matching, mixing, caching, quota and error handling, key masking, the study plan). The real Microsoft Learn and YouTube calls were **not** run: field names follow Microsoft's Catalog API reference and YouTube Data API v3; check the first real response.
- **Not run against live services** (no keys/network were available when this was written): OpenAI LLM/embedding calls, real Chroma, Redis, LangGraph, Langfuse/LangSmith, RAGAS, Unsloth, Udemy Affiliate API. These are wired per each library's documented API and may need small version-specific fixes.
